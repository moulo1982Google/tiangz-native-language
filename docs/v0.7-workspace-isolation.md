# 多工作区语义隔离与实际编辑器验收

2026-09-27，宿主 0.7 联调。

## 失败与修复

实际已安装的 0.16.0 VSIX 在两个文件夹分别声明合法的 `Entity`、`Unit` 和 `@typeId(42)` 时，第二个工程得到 duplicate-entity / duplicate-type-id。原因是语言服务器将全部工作区文档送入同一个语义模型。不是 schema 错误，也不能通过给不同 worktree 分配不同 typeId 解决。

索引现在按工作区文件夹分组，嵌套根采用最长 URI 匹配；没有任何根时保持原独立语言服务器用法，有根时未归属文件独立分析。诊断、补全、Hover、定义、引用、签名与 Quick Fix 使用请求文件的同一作用域。统计仍为整个服务器的汇总，同一工程内的冲突仍报错。解析缓存、输入限制和总扫描上限保留。

增删工作区文件夹会顺序停止、重启同一个 LanguageClient，重建监听并扫描当前源码目录。连续变更合并为一次待刷新标记，关闭时等待当前刷新完成再停止，不为每个根新增语言服务器。源码目录设置仍遵守原来的窗口重载约定。codegen 继续使用当前编辑文件所属目录。

## 验证

- `npm run check`：Core 22 项、Server 9 项通过，包含多根正反例、嵌套根、Hover/导航/typeId 修复隔离和原缓存/性能用例。
- `node tools/check-host-compatibility.mjs --engine ../TiangZ-0.7`：普通、persistent、queued、transactional 四类 21 份生成文本一致，11 份 TS 用宿主 TypeScript 6.0.3 编译通过。无 Core Parser/codegen API 改动。
- `npm run package:extension` 后实际安装 VSIX，核对归档、安装目录、build-info 内两个 bundle 哈希完全一致；以 VS Code 1.139.1 的真正 Extension Host 执行 `extension/test/editor/index.cjs`。
- 实际 Problems 显示并清除工程内重复 typeId，另一工程不受影响；两个目录的 Hover/定义正确；自定义 Shell Task 的 scope/cwd 与活动文件一致；增删第二个目录后旧符号消失、新符号重建。
- 同一窗口安装 Developer Tools 0.15.2：其原任务测试两轮错误/恢复通过；宿主实际实时检查对 Model 中类型合法的 `TimerSystem.Instance.WaitAsync` 给出 time-wait-forbidden，另一工程不报错，恢复源码后清除。

真实编辑器测试要求受信任的可丢弃双目录教学工程，分别准备 schemas/base.native、schemas/unit.native、codegen cwd 标记脚本和官方 starter 模块。可通过普通开发扩展的 activate 调用测试入口；`TIANGZ_EDITOR_TEST_RESULT` 保存 JSON，`TIANGZ_DEVELOPER_EDITOR_TEST` 可指向 Developer 的实际编辑器测试入口。不要全局关闭工作区信任或污染日常扩展目录。

VS Code 1.139.1 的 `--extensionTestsPath` 使用内存存储，首轮未读到隔离信任清单，按预期拒绝执行。改用普通 Extension Host，独立 user-data/extensions/shared-data 目录，只信任两个测试工程及其工作区文件，仍保留 trusted 断言。初始 Developer 夹具未定义 sleep，先得到 TS2304；随后 Hotfix 直接导入 Core 被依赖边界拒绝，均不能证明目标时间规则。改用 Model 稳定入口下的类型合法反例，先经实际宿主 worker 确认，再运行完整编辑器验收。重跑夹具还修正了已打开文档与直接磁盘写入不同步的问题：通过 WorkspaceEdit 修改/保存，再等待诊断；不削弱产品校验。
